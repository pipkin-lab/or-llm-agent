MANDATORY CROSS-CHECK: After extracting all parameters from tables, compute the total implied quantity (e.g., sum of all demands over all periods) and ask: "Is this magnitude consistent with the problem's stated operational scale?" If any objective parameter is still marked [NOT_PROVIDED], perform a TARGETED SCAN: for each index in that parameter's domain (e.g., each truck j in J), search the problem text for any numeric value (dollar amount, fee, rate, cost figure) specifically associated with that index. In any well-posed optimization problem with a finite optimal answer, ALL objective parameters are present in the text. If you cannot locate a value after this targeted per-index scan, re-examine whether the cost is stated implicitly (as a function of capacity, a per-unit rate multiplied by a quantity, or in a footnote/side note). Marking an objective parameter as [NOT_PROVIDED] in a well-posed problem is almost certainly an extraction error — keep scanning until you find it.

If the objective or any constraint contains non-linear terms (squared variables, products of variables, exponential terms, etc.), declare it as QP or NON-LINEAR and note that a non-linear solver (e.g., scipy.optimize) is required rather than a linear solver.
9. BALANCE CONSTRAINT EQUALITY (SUPPLY > DEMAND): In transportation, supply, or allocation problems where total supply exceeds total demand, the supply-side balance constraint MUST be an EQUALITY: (shipped_i + stored_i + disposed_i = S_i) for each origin. Every unit of supply must be explicitly allocated to a downstream activity (shipment, storage, disposal). Using an inequality (<=) on the supply side allows the solver to silently discard excess supply without incurring the associated holding/storage/disposal cost, which underestimates the true objective. Only use <= on the supply side if the problem explicitly states that unused supply has zero cost and no physical consequence.
10. INVENTORY & ACCUMULATION BOUND VERIFICATION: When expressing end-of-period-t inventory or cumulative quantities as a sum over source periods, lots, or cohorts, the summation MUST include the current period t in its upper bound (i.e., sum over i = 1 to t, NOT i = 1 to t-1). End-of-period-t inventory includes all units acquired in period t that remain unconsumed at the end of that period. MANDATORY VERIFICATION: After writing any summation-based inventory or accumulation constraint, substitute t = 1 and confirm the expression captures all first-period acquisitions not consumed in period 1. If the formula yields an empty sum or identically zero for t = 1 while first-period storage is physically possible, the summation bounds are incorrect and must be revised. Additionally, when using lot-tracking or cohort variables (e.g., w[t,k] for "acquired in t, consumed in t+k"), ensure that the capacity or upper-bound constraint on end-of-period-t inventory sums over ALL cohorts still present at that time, including the cohort acquired in period t itself.
11. OBJECTIVE UNIT & NORMALIZATION VERIFICATION: Before finalizing the objective function, verify that the units and scale of the objective value match the exact quantity the problem asks to compute or report. If the problem defines a natural "unit" of measurement (e.g., "one full pass through all N items," "per-unit cost," "in thousands of dollars," "as a fraction of total volume"), the objective MUST be expressed in those units rather than raw absolute counts. QUICK SANITY CHECK: If the problem's context and data suggest the answer should be a small number (single or double digits) but your objective yields a very large number (hundreds of thousands or more), suspect a missing normalization factor. Common cases: (a) the problem measures total workload in "full-batch-equivalent passes" (divide raw item-scans by total items N), (b) the problem asks for average cost per unit (divide total cost by total units), (c) the problem states costs "in thousands" but lists raw dollar values. Always re-read the final question sentence to confirm the exact quantity and its units before locking the objective.
    - MANDATORY PER-UNIT NORMALIZATION: After formulating the objective, re-read the EXACT wording of the final question. If the question asks for a "per-item average," "number of full passes over all N items," "average number of times each unit is processed," or any quantity that is naturally a ratio (total_workload / N_items), the objective MUST include the division by N. Do NOT output the raw aggregate when the question asks for a normalized rate.
    - BASE-UNIT OUTPUT: The objective value reported MUST be in the problem's native/base units (e.g., yuan, not thousands of yuan; seconds, not hours). If you normalize parameters for computational convenience (e.g., dividing all costs by 1000 to work in "thousands"), you MUST multiply the solver's optimal value by the inverse scaling factor before it is reported as the final answer. The Code Agent will report solver.Objective().Value() directly — so the model's objective coefficients MUST already be in the units the problem expects for the final answer.
    - FINAL MAGNITUDE SANITY CHECK (MANDATORY, REPEATED-ERROR GUARD): After formulating the COMPLETE objective (including all coefficients and any division), compute the objective value for a trivial or greedy solution by hand. Then ask: "Does this magnitude match the units the problem's final question implies?" If the question asks for a rate, a count of passes, or a per-unit figure (expected answer: single or double digits) and your greedy-solution objective yields a value in the tens of thousands or higher, you are MISSING a normalization division (typically by N, the total number of items/units). STOP and insert the division into the objective BEFORE finalizing. This check is the last gate before output — do not skip it.
    - CONVERSE MAGNITUDE CHECK (OBJECTIVE TOO SMALL): If your greedy-solution objective is UNREALISTICALLY SMALL relative to the problem's stated operational scale (e.g., the problem involves a factory producing or handling hundreds or thousands of units per period across multiple products, yet your objective is only in the tens of thousands), suspect that a key parameter (demand, capacity, or unit cost) was extracted WITHOUT applying a table-level scale factor. Re-examine every table header, column label, and the sentence immediately preceding or following each table for a multiplier (x10, x100, "in hundreds", "in tens", "百", "十単位"). If found, multiply ALL affected parameter values and recompute the greedy objective. This check catches the mirror-image of the missing-division error: parameters read at face value when the source table uses a coarser unit.
    - NET-CHANGE vs. ABSOLUTE-LEVEL OBJECTIVE: When the problem provides an initial state (initial capital K_0, initial inventory, initial position) and asks for "minimum cost," "minimum investment," "net expenditure," "how much additional money is needed," "minimum net outlay," or "least additional capital required," the objective is the NET CHANGE: (final_value - initial_value), NOT the absolute final level. Formulate as MINIMIZE (K_final - K_0) or equivalently MINIMIZE (total_outflows - total_inflows). Do NOT use MAXIMIZE K_final or MINIMIZE K_final as a proxy. The correct answer may be NEGATIVE (indicating a net profit/surplus). VERIFICATION: If the problem states an initial balance and asks for a "cost," "investment," or "net outlay" figure, check whether your objective equals the absolute final balance or the difference from initial. If it equals the absolute balance, you have an off-by-K_0 error. Subtract the initial value to get the net quantity the problem actually asks for.
12. BOUNDARY-TIME EVENT INCLUSION: When a financial obligation (loan principal repayment, bond maturity, lease end, penalty) is stated to occur "at the end of [final period] of next [time unit]" and the objective is evaluated at "the beginning of next [time unit]," these describe the SAME time point. The obligation MUST be included as a cash outflow in the final period's balance. Do NOT exclude a boundary event on the grounds that it occurs "after" the objective evaluation unless the problem provides two explicitly distinct timestamps (e.g., "end of December" vs. "end of January"). DEFAULT RULE: If the repayment/maturity language references the same calendar period as the last period of the planning horizon, include it in the final period equation. Excluding it renders the model unbounded (the solver can inflate the loan principal without penalty) or structurally infeasible.
13. FLEET / VEHICLE WORKLOAD SCOPE (ONE-WAY vs. ROUND-TRIP):
    - For a ONE-WAY route O→D, the service time per sailing is: t_load + t_OD + t_unload. The return leg D→O is REPOSITIONING (deadhead), NOT service.
    - WORKLOAD per route r = frequency_r × (t_load + t_OD,r + t_unload). Do NOT add t_DO,r (return transit) to the service duration.
    - Total fleet workload = sum over all routes of (frequency_r × service_time_r).
    - COMMON ERROR (OBSERVED REPEATEDLY): Computing "cycle time" as load + sail_OD + unload + sail_DO for one-way routes. This DOUBLES the transit component and inflates the answer. The return leg is only part of the service if the problem EXPLICITLY states the vehicle must return to the same origin to repeat the identical route (a closed-loop requirement). If the problem says "route A to B" with a given daily frequency, the service is A to B only.
    - VERIFICATION: After computing the total workload, check whether the answer makes sense as a fleet size. If it seems too large (exceeding the sum of frequencies by a factor equal to the round-trip time rather than the one-way time), you likely included return legs incorrectly. Recompute using one-way service time only.
    - REPOSITIONING INCLUSION: Only add repositioning/deadhead time to the objective if the problem EXPLICITLY requires it (e.g., "count total vehicle-days including repositioning" or a time-window constraint that forces waiting). Otherwise, the objective is service workload ONLY.
14. SHIFT/SCHEDULE COVERAGE CONSTRAINT FORMULATION: In shift scheduling or staff coverage problems, the demand constraint for each time period is: (SUM of ALL shift variables that have ANY temporal overlap with that period) >= Demand_period. Even if two shifts covering different sub-portions of a period do NOT overlap with each other (e.g., one shift ends at 02:00 and the next starts at 02:00 within a 22:00–06:00 period), they are BOTH included in the same single sum constraint for that period. Do NOT decompose a demand period into sub-segments and create separate per-segment constraints. The period is a single unit of demand met by the aggregate of all shifts touching it.
    - VERIFICATION: After writing all coverage constraints, for each period, list which shifts overlap and confirm they all appear in a single sum. If you wrote separate constraints for sub-intervals within one period, merge them into a single sum constraint.
    - COMMON ERROR: Splitting a period where two non-overlapping shifts each cover part of it into two independent >= demand constraints. This over-constrains the model and inflates the optimal workforce. The correct form is a single sum constraint including both shift variables.
15. BOTTLENECK / MIN-MAX OBJECTIVE (SERIAL SYSTEMS): When the problem asks to maximize "overall production capacity," "throughput," "output rate," "processing speed," "line speed," or any aggregate performance measure of a SERIAL or MULTI-STAGE system (assembly line, pipeline, sequential workflow where every unit must pass through ALL stages), the objective is the MINIMUM (bottleneck) across all stages, NOT the sum.
    - FORMULATION: Introduce auxiliary variable Z (the system throughput / bottleneck rate). MAXIMIZE Z. Subject to: (throughput of stage s) >= Z for EVERY stage s. In an assignment context (assign workers to stations in a serial line), the constraint for each station s is: (sum over workers w of efficiency[w,s] * x[w,s]) >= Z.
    - DISAMBIGUATION: Use the SUM objective ONLY when the problem explicitly says "total output," "sum of rates," "aggregate capacity," or describes PARALLEL independent tasks. Use the BOTTLENECK (min) objective when the problem describes a LINE, PIPELINE, SEQUENCE, or ASSEMBLY where items must pass through all stages in order.
    - COMMON ERROR: Formulating max(sum of efficiencies) for a serial assembly line. This ignores that the slowest station limits the entire line's output. The sum objective overestimates capacity by ignoring the bottleneck.
    - VERIFICATION: After formulating, ask: "If one station is 2x slower than all others, does my objective reflect that the whole system is 2x slower?" If the answer is YES (objective drops to the bottleneck), the formulation is correct. If NO (objective barely changes), you likely used the sum instead of the bottleneck.
16. CASH FLOW / FINANCIAL BALANCE COMPLETENESS: In multi-period cash flow, loan, or financial planning models, the period-t balance equation B_t MUST include EVERY cash inflow and outflow that occurs during period t. Specifically:
    - A loan or investment PRINCIPAL RECEIVED at the start of period t MUST appear as +L in B_t. Omitting it forces the solver to set L=0 (since L then only appears as negative interest/repayment terms in later periods), producing a suboptimal or infeasible solution.
    - A loan PRINCIPAL REPAID at the end of period t MUST appear as -L in B_t.
    - INTEREST payments due during period t MUST appear as -r*L in B_t.
    - Deposit or investment PROCEEDS (principal + interest) received at the end of period t MUST appear in B_t.
    - COMMON ERROR: Writing B_1 = S_1 + r_D*D_1 + c_1 for a period where a loan L is also received, thereby omitting +L. The variable L then only appears with negative coefficients in B_2..B_T, the LP forces L=0, and the solution is wrong.
    - MANDATORY VERIFICATION (CASH FLOW TRACE): After writing all balance equations, for EACH financial instrument variable (loan, deposit, bond, investment), explicitly list: (a) the period and sign of the principal receipt, (b) the periods and sign of each interest/coupon payment, (c) the period and sign of the principal repayment/redemption. Confirm each entry appears in the correct B_t equation. If any entry is missing, add it before finalizing.
17. SYMMETRIC PAIR DOUBLE-COUNTING IN BILINEAR / QUADRATIC OBJECTIVES: When the objective contains a bilinear or quadratic term of the form (sum over i, k of C[i,k] * f(i,k)) where the coefficient matrix C is SYMMETRIC (C[i,k] = C[k,i]) and the summation runs over ALL ordered pairs (i,k) with i ≠ k, each unordered pair (i,k) is counted TWICE.
    - CORRECT FORMULATION (MANDATORY): Restrict the summation to i < k ONLY (each unordered pair appears exactly once). State this restriction explicitly in the Index Sets section.
    - ALTERNATIVE: Keep the full (i,k) summation over all i ≠ k BUT include a factor of 1/2 in the objective.
    - COMMON ERROR: Writing the objective as "sum over all i ≠ k" for a symmetric cost/volume matrix, noting in a remark that "one could restrict to i < k," but then proceeding with the unrestricted sum. The Code Agent will implement exactly what is written in the summation bounds. If the bounds say "for all i, k with i ≠ k," the double-counting WILL occur.
    - VERIFICATION: For a 2-entity problem (only i=1, k=2), the interaction cost should appear ONCE in the objective, not twice. If your 2-item sub-problem yields 2 * C[1,2] * D instead of C[1,2] * D, the summation is double-counting.
    - SCOPE: This applies to ANY bilinear/quadratic objective with a symmetric interaction matrix (facility location, quadratic assignment, network design with undirected edges, etc.).
18. TRANSPORTATION FLOW PINNING (SUPPLY < DEMAND COMPLEMENT TO RULE 9): In transportation, transshipment, or allocation LPs where ALL unit costs are strictly positive, if BOTH the supply-side and demand-side balance constraints are written as inequalities (<=), the trivial solution (ship nothing, x = 0) is optimal and the objective is 0.
    - SUPPLY < DEMAND CASE: When total supply is LESS than total demand, the supply-side constraint MUST be an EQUALITY (sum of all outflows from the source = total supply). The demand side may remain an inequality (<=) to allow unmet demand. Example: sum(y_i) = 270 (factory produces all 270 tons), sum(x_ij) <= D_j (some regional demand may go unmet).
    - SUPPLY = DEMAND CASE: Both sides are equalities.
    - SUPPLY > DEMAND CASE: Covered by Rule 9 (supply side = equality with explicit disposal/storage).
    - COMMON ERROR: Writing sum(y_i) <= S_total when S_total < total demand. The solver sets y_i = 0 for all i, yielding objective = 0.
    - VERIFICATION: After writing all flow constraints, ask: "Can the solver satisfy every constraint by setting all flow variables to zero?" If YES and the problem context requires actual shipping/production, at least one balance equation is missing an equality.
19. PRODUCTION PLANNING: DIRECTION & DEMAND CONSTRAINT VERIFICATION: In multi-stage production, flow-shop, or job-shop planning problems (products pass through sequential stages on multiple machines), perform the following MANDATORY checks BEFORE finalizing:
    - (a) OPTIMIZATION DIRECTION: Re-read the EXACT final question. If it asks "minimum total cost," "least cost," "cheapest production plan," or "minimum cost to meet demand," the objective is MINIMIZE (total processing cost + material cost), NOT maximize profit. If it asks "maximum profit," "maximum output value," or "maximum revenue," use MAXIMIZE. Do NOT default to profit maximization unless the problem explicitly frames it that way.
    - (b) DEMAND / TARGET CONSTRAINTS: If the problem specifies production targets, order quantities, minimum output levels, or customer demand for each product (e.g., "produce at least 200 units of Product A," "demand for Product B is 150 units," "an order of 300 units must be fulfilled"), these MUST appear as explicit constraints: Q_p >= D_p (or Q_p = D_p if exact). A maximization WITHOUT demand bounds will push all production variables to machine-capacity limits, yielding an objective value orders of magnitude larger than the expected answer.
    - (c) CAPACITY-TO-DEMAND RATIO CHECK: After identifying both machine capacities and demand targets, compute the ratio: (total available machine-minutes) / (total processing-minutes required to meet demand). If this ratio is very large (>10), the problem is demand-driven (demand constraints are binding, capacities are slack). In this case, the objective is determined by demand quantities, NOT by capacity utilization. If you formulated a maximization without demand constraints, the solver will exploit the slack and produce a result 10x+ too large.
    - (d) COMMON ERROR (OBSERVED): Formulating a production planning problem as MAXIMIZE profit with only capacity constraints (no demand targets). The solver saturates every machine to capacity, producing an objective ~50-100x the correct answer. The fix: add the demand constraints AND verify the optimization direction matches the problem's question.
    - VERIFICATION: After formulating, estimate the expected objective magnitude from the demand quantities and per-unit economics. If your model's boundary solution (all machines at capacity) yields a value >10x the demand-based estimate, you are missing binding demand constraints or have the wrong direction.
20. MTZ SUBTOUR ELIMINATION (TSP / ROUTING): When using the Miller-Tucker-Zemlin (MTZ) formulation for TSP, VRP, or any single-vehicle routing problem requiring a single Hamiltonian cycle:
    - DESIGNATE A ROOT NODE: Select one node (e.g., city 1) as the root. Fix u_root = 0 (or u_root = 1, depending on convention).
    - RESTRICTED CONSTRAINT DOMAIN (MANDATORY): The MTZ subtour elimination constraint u_i - u_j + N*x_ij <= N-1 is written ONLY for pairs (i, j) where BOTH i and j are in N\<curly_brackets>root</curly_brackets> AND i ≠ j. The root node is EXCLUDED from the MTZ constraint set.
    - FORBIDDEN: Writing MTZ constraints involving the root node (i.e., any constraint where i = root or j = root). Including them makes the model INFEASIBLE because the inflow conservation constraint forces x_i,root = 1 for some i ≠ root, and the MTZ constraint for that arc becomes u_i - 0 + N*1 <= N-1, i.e., u_i <= -1, which contradicts u_i >= 0.
    - VARIABLE BOUNDS: u_root = 0 (fixed); 0 <= u_k <= N-1 for all k ≠ root.
    - FLOW CONSERVATION: The root node participates ONLY in the standard flow conservation (indegree = 1, outdegree = 1) constraints, NOT in the MTZ subtour elimination set.
    - VERIFICATION (MANDATORY): After writing all MTZ constraints, explicitly list the index set over which they are quantified. Confirm it is N\<curly_brackets>root</curly_brackets> × N\<curly_brackets>root</curly_brackets> minus the diagonal. If any constraint references u_root or involves the root index, DELETE it. Ask: "Does the inflow constraint on the root node conflict with any MTZ constraint?" If yes, the root was incorrectly included in the MTZ domain.
